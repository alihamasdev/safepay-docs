description: |-
  Perform the `AUTHORIZATION` action.

  Note that you will call Authorization when enrollment was frictionless (i.e. no challenge was applicable) or if enrollment could not be completed by the issuer.If enrollment follows up with the challenge and the customer has been redirected to your checkout, then you must proceed to Capture instead.

  For this action, you need to pass in the `authorization` configuration.

  ### Action chaining

  Actions are chained by default by the Order API where actions that do not require additional input from the client will execute in a loop. Since `CAPTURE` is one such action, it will be chained and executed even when `authorization.do_capture` is set to false.

  Setting `authorization.do_capture` to true essentially performs a ***sale*** as opposed to an authorization followed by capture.

  If you wish to perform captures manually, you may run this request by setting `use_action_chaining` to false in the request body (outside of the `payload`). This will then only perform the `AUTHORIZATION` action and allow you to perform the capture (or a reversal) at a later time.

  ### Authorizing CITs

  When we set the `mode` to `payment` and the `entry_mode` to `network_token` in the **setup** api, we are initating a **CIT** (Customer Initiated Transaction). When we are dealing with **Network Tokens**, the next action after setup will be **AUTHORIZATION**, so we will have to send the extra information in the Authorization request which we otherwise wouldn't have needed to. This includes the **Billing** information, as well as the **Payment Method** in the form of a **Network Token.** As per usual the authorization settings are also required. The response will include a **TMS-Token** that can be used for subsequent MITs. The response contains the tms token like so: `action.token.payment_method.token: "tms_ea7323a9......".`

  ### Authorizing MITs

  When we set the `mode` to `subscription` and the `entry_mode` to `mit` in the **setup** api, we are initating a **MIT** (Merchant Initiated Transaction). **MITs** function fairly similarly to **Subscriptions** with **TMS** tokens, since in this case you are expected to pass a **TMS** token in the request alongside the authorization settings. However, a **MIT** must always have an attached **CIT**. As mentioned above a CIT can be initated using a Network Token, however a `raw` payment will also work, as long as the `do_card_on_file` setting was set to true and a pm_ token was returned in the response. This token can also be used for MITs.
