description: |-
  Perform the `PAYER_AUTH_ENROLLMENT` action. This marks the start of the payer authentication process. For details please refer to the Cybersource [Payer Authentication](https://developer.cybersource.com/docs/cybs/en-us/payer-authentication/developer/all/so/payer-auth/pa-about-guide.html) documentation.

  As the documentation states, there are 5 steps for the complete process. Note that Steps 1, 3, and 5 are to be performed server side and are handled by the Safepay API. You will need to perform [Step 2: Device Data Collection](https://developer.cybersource.com/docs/cybs/en-us/payer-authentication/developer/all/so/payer-auth/pa2-ccdc-ddc-intro.html) before calling this action. And you will need to perform [Step 4: Step-Up Iframe](https://developer.cybersource.com/docs/cybs/en-us/payer-authentication/developer/all/so/payer-auth/pa2-ccdc-stepup-frame-intro.html) after receiving the response for this action.

  To succeed enrollment and trigger liability shift you must pass the `device_fingerprint_session_id` which you will obtain after performing [Step 2: Device Data Collection](https://developer.cybersource.com/docs/cybs/en-us/payer-authentication/developer/all/so/payer-auth/pa2-ccdc-ddc-intro.html).

  You must provide the customer's billing details under `payload.billing`:

  If you do not have this information, you may instruct the API to generate synthetic data by making use of the `use_synthetic` field as shown below:

  ```json
  "payload": {
    ...
    "billing": {
      "use_synthetic": true
    }
    ...
  }
  ```

  You must also provide authorization configuration under `payload.authorization`. Additional configuration options will be made available in the future. We recommend this default:

  You must also provide payer authentication configuration under `payload.authentication_setup`:

  You must also authenticate using JWT that represents the guest user. Refer to the documentation for *API Authentication*.

  Note that while `device_fingerprint_session_id` is optional, not passing it will default to 3DS v1 on Cybersource's end which they have dropped support for. Therefore to ensure successful enrollment and liability shift, you should include this in the request.

  ### Interpreting the enrollment response

  If enrollment is successful, you should obtain the appropriate ECI values and the `access_token` in the `payer_authentication_enrollment` object.

  The response will also yield an `authentication_status` field that may take the following values. Here is how to interpret these:

  The values for `eci` or `eci_raw` denote whether enrollment was successful:

  Rendering the issuer step-up challenge is documented in [Step 4: Step-Up Iframe](https://developer.cybersource.com/docs/cybs/en-us/payer-authentication/developer/all/so/payer-auth/pa2-ccdc-stepup-frame-intro.html).

  The user will go through the 3DS flow by entering the OTP code received on their phone (or alternative methods proposed by the issuer). On a successful response, the user will be redirected to Safepay and then ultimately to the `success_url` that you have provided. Similarly, failures will redirect to the `failure_url`.

  Returning to the `success_url` yields a successful authorization. Note that for the frictionless flow you may proceed to authorization.
